# Refactoring Documentation

## Purpose

This directory centralises all documentation related to **refactoring**, **technical debt**, **performance optimisation**, **testing gaps**, and **legacy UI cleanup** for the SOC5‑Outbound project. It serves as the single source of truth for tracking improvement opportunities identified during implementation sprints.

## How Codex Implementation Reports Are Processed

1. **Codex PR Merge** – After a sprint, the implementation PR generated by Codex is reviewed.
2. **Identify Opportunities** – Review the PR description, inline comments, and any autogenerated "Implementation Findings" section.
3. **Create Backlog Entry** – For each refactoring opportunity, add a row to `REFACTORING_BACKLOG.md` (or the appropriate template file) following the defined schema.
4. **Assign Ownership** – Tag the responsible owner (e.g., component lead) in the entry.

## Gemini Backlog Maintenance

- A nightly Gemini script (`generate_backlog`) parses merged PRs for the labels `refactor`, `perf`, `test-gap`, etc., and automatically appends a **skeleton** row to the appropriate markdown file.
- The script respects the priority and status definitions listed below.

## Priority Definitions

| Priority | Meaning |
|----------|---------|
| **Critical** | Immediate business impact; must be addressed before the next release. |
| **High** | Significant impact on performance, reliability, or maintainability; schedule for the upcoming sprint. |
| **Medium** | Moderate impact; can be planned for a future sprint. |
| **Low** | Minor annoyance or cosmetic issue; optional backlog item. |

## Status Definitions

| Status | Description |
|--------|-------------|
| **Open** | Identified but not yet evaluated. |
| **Planned** | Approved and scheduled for a future sprint. |
| **In Progress** | Actively being worked on. |
| **Completed** | Refactoring done and verified. |
| **Deferred** | Deliberately postponed (record reason in **Notes**). |
